# Лабораторная работа №1: Проектирование сервиса сокращения URL

## Постановка задачи

Необходимо спроектировать сервис сокращения URL, аналогичный **TinyURL**.  
Сервис должен принимать длинный URL и возвращать уникальный короткий URL.  
При переходе по короткому URL пользователь должен быть перенаправлен на исходный длинный URL.

---

## Функциональные требования

1. Пользователь может ввести длинный URL и получить короткий.  
2. При переходе по короткому URL происходит HTTP-редирект на оригинальный URL.  
3. Пользователи могут задавать кастомные короткие URL (псевдонимы).  
4. Короткие URL должны иметь ограниченный срок действия (например, 1 год).

---

## Нефункциональные требования

1. **Высокая доступность:** сервис должен быть доступен 99.9% времени.  
2. **Низкая задержка:** редирект должен происходить <100 мс.  
3. **Масштабируемость:** система должна поддерживать до 10 млн новых URL в месяц.  
   Соотношение чтений (редиректов) к записям (создание URL) — **100:1**.

---

## Выполнение

По теореме CAP реализуется **CP**, доступность повышается за счёт кеширования и очередей.

### 1. Оценочные расчёты

#### Расчёт QPS

**Запросы на запись (создание URL):**
10 млн / (30 \* 24 \* 3600) ≈ 4 RPS

**Запросы на чтение (редирект):**
10 млн \* 100 / (30 \* 24 * 3600) ≈ 386 RPS

#### Объём хранилища

10 млн \* 12 мес \* 5 лет = 600 млн записей
Размер записи = 2089 байт
Итого: 600 млн \* 2089 байт ≈ 1.14 ТБ

---

### 2. Проектирование API

#### Проверка короткого URL

**Эндпоинт:**  
GET /{short_key}

**Успешный сценарий:**
302 Found
Header: Location: <original_long_url>

**Ошибки:**

- `404 Not Found` – ссылка не найдена

```json
{
  "error": "URL_NOT_FOUND",
  "message": "The requested short URL does not exist",
  "short_key": "abc123"
}
```

- `410 Gone` – ссылка просрочена по сроку использования

```json
{
  "error": "URL_EXPIRED",
  "message": "This short URL has expired and is no longer active",
  "short_key": "abc123",
  "expired_at": "2024-01-01T00:00:00Z"
}
```

- `400 Bad Request` – некорректный формат короткой ссылки (содержит недопустимые символы)

```json
{
  "error": "INVALID_SHORT_KEY",
  "message": "Short key contains invalid characters",
  "short_key": "ab@c12!",
  "allowed_characters": "a-z, A-Z, 0-9, hyphen, underscore"
}
```

#### Создание короткого URL

**Эндпоинт:**

POST /api/v1/urls

**Тело запроса (JSON):**

```json
{
  "long_url": "https://www.example.com/very/long/with_huge_and_difficult_parametres",
  "custom_alias": "my-custom-link",
  "expiry_days": 365
}
```

Успешный ответ:

- `201 Created`

```json
{
  "short_url": "https://short_url",
  "long_url": "https://www.example.com/very/long/with_huge_and_difficult_parametres",
  "expires_at": "2025-04-23T18:25:43Z",
  "created_at": "2024-04-23T18:25:43Z"
}
```

Ошибочный сценарий:

- `409 Conflict` - custom_alias уже занят другим пользователем:

```json
{
  "error": "ALIAS_ALREADY_EXISTS",
  "message": "The requested custom alias is already in use",
  "alias": "my-custom-link",
  "suggestion": "my-custom-link-123"
}
```

## 3. Модель данных

### Тип БД: SQL

**Обоснование выбора:**

- Данные структурированы и имеют фиксированную схему.  
- Необходимо удалять просроченные ссылки — в SQL это реализуется проще.  
- SQL предоставляет транзакционность (ACID), что важно для корректности и уникальности данных.  

### Схема таблицы

| Поле        | Тип данных            | Размер | Описание                                   |
|--------------|-----------------------|--------|---------------------------------------------|
| id           | BIGINT AUTO_INCREMENT | 8      | Первичный ключ                              |
| short_key    | VARCHAR(20)           | 21     | Уникальный индекс, короткая часть URL       |
| long_url     | VARCHAR(2048)         | 2050   | Исходная длинная ссылка                     |
| created_at   | TIMESTAMP             | 4      | Дата и время создания ссылки                |
| expires_at   | TIMESTAMP             | 4      | Дата и время окончания срока действия       |
| is_custom    | BOOLEAN               | 1      | Флаг, указывает, является ли ссылка кастомной |
| is_active    | BOOLEAN               | 1      | Флаг активности ссылки                      |

## 4. Технические решения

### Алгоритмы генерации коротких ключей

#### 1. Base62 от хеша (MD5 / SHA-256)

- **Описание:** Берётся хеш от длинного URL + соль (timestamp или случайное число). Первые N байт хеша кодируются в Base62.  
- **Плюсы:**  
  - Детерминированность — один и тот же URL всегда даёт одинаковый ключ.  
  - Не требуется хранение состояния.  
- **Минусы:**  
  - Возможны коллизии (хотя вероятность низкая).  
  - Непоследовательные ключи.  

#### 2. Инкрементальный счётчик + Base62

- **Описание:** Используется автоинкрементный ID из БД, затем кодируется в Base62.  
- **Плюсы:**  
  - Гарантированная уникальность.  
  - Простота реализации.  
- **Минусы:**  
  - Централизованный генератор ID может стать узким местом.  
  - Ключи предсказуемы.  

#### 3. Случайная строка (Base62)

- **Описание:** Генерируется случайная строка длиной 6–8 символов из алфавита Base62.  
- **Плюсы:**  
  - Высокая непредсказуемость.  
  - Простая реализация и масштабирование.  
- **Минусы:**  
  - Необходима проверка уникальности в БД.  
  - Возможны редкие коллизии.  

#### 4. Snowflake-like генерация

- **Описание:** Генерация 64-битного числа из следующих компонентов:  
  - **Timestamp (41 бит)** — миллисекунды с эпохи (~69 лет).  
  - **Node ID (10 бит)** — уникальный ID инстанса (до 1024 нод).  
  - **Sequence (12 бит)** — последовательный номер (до 4096/мс).  
  Затем число кодируется в Base62 (≈11 символов).  
- **Плюсы:**  
  - Уникальность без координации между нодами.  
  - Высокая производительность, генерация в памяти.  
  - Время встроено в ID, что упрощает отладку и шардирование.  
- **Минусы:**  
  - Требуется управление уникальными Node ID.  
  - Ключи немного длиннее.  

**Рекомендация:**  
Использовать **Snowflake-like генератор + Base62** — оптимальное решение по балансу уникальности, масштабируемости и производительности.

---

### Обработка кастомных псевдонимов и конфликтов

1. Пользователь отправляет запрос `POST /api/v1/urls` с параметром `custom_alias`.  
2. Сервис проверяет наличие `short_key = custom_alias` в БД.  
3. Если алиас существует и активен — возвращается `409 Conflict`.  
4. Если алиас свободен — создаётся запись с `is_custom = true`.

---

### Стратегия кеширования

**Технология:** Redis  
**Тип:** Read-Through Cache  

**Ключ:** `short_key`  
**Значение:** Полная запись из БД (включая `long_url`)

#### Логика работы

1. При запросе `GET /{short_key}` сначала проверяется кэш.  
2. При попадании в кэш — мгновенный редирект.  
3. При промахе — запрос к БД и сохранение результата в кэш (TTL, например, 24 ч).  
4. При истечении срока действия ссылка удаляется из кэша.

#### Расчёт объёма и конфигурации Redis

- **Нагрузка:** 386 RPS на чтение  
- **Размер одной записи:** ~170 байт (20 + 100 + 50)
- **Кэшируемые данные:** 20% «горячих» ссылок  

10 млн \* 100 \* 20% = 200 млн активных записей
200 млн * 170 байт ≈ 34 ГБ

#### Рекомендации

- Использовать **Redis Cluster** для шардирования.  
- 64–128 ГБ RAM.  
- Политика вытеснения: `allkeys-lru`.  
- TTL: оставшееся время жизни ссылки, но не более 7 дней.

## 6. Анализ узких мест

| Потенциальная проблема | Описание | Решение |
|------------------------|-----------|----------|
| **Генерация ключей** | Централизованный автоинкремент вызывает узкое место | Использовать Snowflake или случайные строки |
| **Высокая нагрузка на чтение** | 386 RPS к БД | Кэширование в Redis, CDN |
| **Рост таблицы** | Снижение скорости запросов | Партиционирование по `created_at`, индексы на `short_key`, `expires_at` |
| **Злоупотребление API** | Спам, подбор алиасов | Rate Limiting (по IP / API-ключу) |
| **Пиковые нагрузки на запись** | Очереди фоновых задач | RabbitMQ: кэширование, аналитика, инвалидация ссылок |

### Архитектура с очередями (RabbitMQ)

1. API-сервис выполняет синхронно только критичные операции:  

- Проверка уникальности `custom_alias`.  
- Сохранение записи в PostgreSQL.  

2. После сохранения — асинхронная постановка задач в очередь:  

- Обновление кэша (Redis).  
- Отправка аналитики.  
- Планирование удаления просроченных ссылок.

**Преимущества:**

- Буферизация пиковых нагрузок.  
- Ускорение отклика API.  
- Повышение надёжности (гарантированная доставка сообщений).
